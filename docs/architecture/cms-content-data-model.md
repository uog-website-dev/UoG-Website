# Site-scoped CMS content data model (P2-CMS-001)

Implementation date: 2026-10-29. This story initializes the shared CMS
domain: one Django `cms` app, one content base record that Pages, Posts and
later content types inherit, and registry codes for the capabilities built
on top of it. CMS exposes only scoped workflow and revision-management
endpoints, not generic content CRUD or public serving.

## Fields

| Field | Contract |
| --- | --- |
| id | UUID primary key, assigned once, `editable=False`, immutable at the domain layer. UUIDs are not sequential, so ids never leak how many records another Site owns and cannot be enumerated across Sites |
| site | Required FK to `sites.Site`, ORM `PROTECT` and a real PostgreSQL foreign key, related name `content`. Content cannot be moved between Sites after creation |
| status | `DRAFT`, `IN_REVIEW`, `APPROVED`, `PUBLISHED`, `UNPUBLISHED` or `ARCHIVED`; new records start `DRAFT`. See [cms-workflow.md](./cms-workflow.md) |
| locale | Normalized language tag in the same format as `Site.default_language` (`en`, `am`, `en-us`, …), 35 characters. Empty inherits the Site default; an explicit value must be enabled for that Site. Storage format only — no translation workflow is claimed |
| published_at | Nullable timestamp set on the first publish and kept as history if the record later returns to `DRAFT` or `ARCHIVED` |
| created_by / updated_by | Nullable FKs to the local platform user (`settings.AUTH_USER_MODEL`, `SET_NULL`). Write services set them from the authenticated principal; they are never accepted from a request body. Removing an account keeps the content and clears the attribution |
| submitted_by / reviewed_by / review_comment | Server-managed workflow attribution and the latest reviewer comment. Full transition history is append-only in `ContentWorkflowTransition` |
| metadata | JSON object (`jsonb_typeof = 'object'` check constraint). Free-form approved content metadata, never a settings document and never secrets |
| revision_number | Server-managed optimistic concurrency token, incremented on every meaningful save and matched to an immutable `ContentRevision` |
| created_at / updated_at | Timezone-aware automatic timestamps; every save updates `updated_at` |

Model writes normalize `locale`, run `full_clean()` and enforce the rules
below before the row reaches the database, matching the Site and Organization
conventions.

## Immutable identity and site ownership

`id` is generated by the domain (`uuid.uuid4` default) and never changes: an
existing record whose primary key no longer resolves is rejected with
"Content identifiers are immutable", and `editable=False` keeps it out of
forms and serializers. `site` is fixed at creation; re-parenting raises
"Content cannot be moved between Sites". The `PROTECT` relation means a Site
that still owns content can never be removed from under it.

## Site-scoped uniqueness and index strategy

CMS uses the one shared PostgreSQL database and schema — there is no
per-Site database or schema anywhere in the platform. Every tenant
separation is expressed in the rows themselves:

- **Identity is per record, not per table.** The UUID primary key is the only
  globally unique value. The base record has no global natural key (no
  platform-wide slug), so nothing about content is unique *across* Sites by
  accident.
- **Children scope uniqueness by leading with `site`.** When a content type
  adds its own natural key — for example a slug — it must be a unique
  constraint on `(site, slug)`, never a global `unique=True`. Uniqueness is
  therefore "one slug per Site", and two Sites may reuse the same value.
- **Indexes lead with the ownership column.** Every query for content is
  scoped by Site first, so the base declares `cms_content_site_status_idx`
  `(site, status)` for lifecycle listings, `cms_content_site_recent_idx`
  `(site, -updated_at)` for recency-ordered listings, and relies on the
  automatic foreign-key index on `site_id` for exact owner lookups. Author
  lookups use the automatic `created_by`/`updated_at` FK indexes. No
  speculative search-engine or cross-tenant index is introduced.
- **Revision history is owner-scoped.** `cms_revision_site_recent_idx`
  indexes `(site, content, -revision_number)` for tenant-filtered revision
  lists. A unique `(content, revision_number)` constraint makes version
  allocation deterministic under the content row lock.

## Locale

`locale` deliberately reuses `Site.default_language`'s constrained format
(2–3 letter primary subtag, optional 2–8 character alphanumeric subtags).
When a record omits it, it resolves to the Site's default language; when it
is explicit, it must appear in the Site's `configuration.language.enabled`
list, so content can only claim a language the Site actually offers. This
models compatibility with enabled languages; it does not implement
translation, fallback or a translated-content catalog — those belong to the
multilingual stories.

## Module gating

`PAGES`, `POSTS` and `MENUS` are seeded registry rows. P2-CMS-006 ships PAGES
and records it as `IMPLEMENTED`; its global switch remains off by default.
Public Page delivery additionally requires PAGES to be enabled for the
resolved Site. Menu rows ship with the menu tree: MENUS is `IMPLEMENTED`
and recorded in `sites_module_implementation`, and its global switch stays
off until an operator enables it. A Site can store menu edits only while
MENUS is enabled for that Site. Turning the module off leaves the rows in
place and rejects later saves. POSTS remains planned and cannot be enabled.
See the [module registry](module-registry.md).

### Menu trees (P2-MENU-001)

`cms.Menu` owns one Site and one registered location: `header`, `footer`,
`sidebar`, `primary` or `secondary`. These configured location keys are a
controlled deployment contract; extending them requires a reviewed migration
and an update to `MENU_LOCATIONS`. The unique `(site, location)` constraint
allows the same location in different Sites. Menus and items have active flags.

`cms.MenuItem` uses an adjacency list, immutable menu/Site ownership, UUID
identifiers and a maximum of four levels (root is level one). Sibling order
is unique including root siblings, with `(sort_order, id)` deterministic reads.
`selectors.menus.menu_tree` loads at most 1,001 items in one item query and
rejects trees above its 1,000-item default response limit. Inactive branches
hide their entire subtree unless an authorized caller explicitly asks
to include inactive items. This selector is administrative, not public delivery.

The `0008_menu_menuitem` migration creates the schema and registers MENUS;
`0009_menu_integrity` adds the active flag, location constraint and PostgreSQL
guards. Database triggers protect ordinary, bulk and raw writes against cycles,
depth violations (including moved descendants), menu/Site mismatches, invalid
target combinations, unsafe URLs and disabled modules. The common transactional
guard serializes menu, module-switch and Post-owner changes before row locks.
The guard revision rejects stale repeatable-read snapshots. Deactivation never
deletes rows, and editing or deleting them while MENUS is off is rejected.
The integrity migration rejects invalid legacy data rather than leaving a bad
tree in place; valid records can migrate with MENUS disabled.

User-facing callers use `services.menus`, which resolves ownership from saved
rows and checks active, database-backed `content.menus.view/manage` grants at
platform, organization or Site scope. Standard platform, organization and Site
administrators receive these capabilities when `seed_rbac` reconciles roles.
Unassigned, inactive, anonymous and foreign-Site actors are rejected. Direct
model writes are trusted system operations, as with other domain models.

Internal Page/Post links require an existing target in the same Site by default.
The explicit `allow_cross_site` policy permits foreign targets only when the
user also has the relevant content-view permission for the target Site. A flag
in a request never supplies that permission. Referenced Post-owner changes that
would invalidate a link are blocked; Page ownership is already immutable.
Targets are PROTECT references. Rendering must still apply content publication
and visibility rules; a menu link does not publish its target.

External targets accept only well-formed HTTP(S) URLs without credentials,
control characters, encoded controls/backslashes, ambiguous escaping or invalid
ports. Custom targets are restricted to normalized same-Site paths. This layer
stores links and never follows external URLs or issues redirects; it cannot
certify the behavior of an external server. No Menu HTTP endpoint is introduced
by the model foundation story. The subsequent
[Menu administration API](../development/menu-api.md) exposes scoped CRUD and
atomic tree mutations, adds a Menu-wide version in `0010_menu_api_contract`,
and records shared durable audit events. The current OpenAPI includes those
authenticated routes. See the historical [model audit](../development/menu-audit.md).

## API contract

`apps.cms.api.serializers.SiteContentSerializer` is the shared serialization
contract: `id`, `site`, workflow state, revision number, `published_at`,
authorship and timestamps are server-managed and read-only; unknown or
immutable fields are rejected explicitly. The site-scoped workflow and
revision-management routes are documented in the
[OpenAPI snapshot](../api/openapi.yaml) and [workflow contract](cms-workflow.md).
Page management is exposed through the Site-scoped authoring API and public
host-resolved delivery API described in [cms-pages](../api/cms-pages.md).

## Revisions and optimistic concurrency (P2-CMS-005)

Each creation and meaningful save stores a complete, immutable JSON snapshot
with its editor identity, timestamp, status, changed fields and SHA-256 hash.
The `revision_number` token detects stale ORM instances; a stale save raises
`ContentEditConflict`. Revision history is Site-scoped in the API, and a
restore requires a current `If-Match` ETag and creates a new DRAFT revision.
Published snapshots and published-status revisions are never edited.

Snapshots are capped at 1 MiB. The newest 100 non-published revisions are
retained, with all PUBLISHED revisions and revisions referenced by a restore
kept indefinitely. Older eligible drafts are pruned transactionally.
PostgreSQL triggers require a corresponding immutable revision for each
content version and reject direct content changes that bypass the revision
service.

## Structured blocks (P2-CMS-003)

Every content type on `SiteContent` — pages today, posts when they ship —
carries an ordered, versioned list of typed block objects (`blocks` +
`blocks_version`): heading, paragraph (sanitized rich text), image, button,
list and the optional section container. The schema, its validators, and
the safe-rendering and asset-scope contracts are documented and versioned
in [cms-content-blocks](cms-content-blocks.md); one schema is reused by all
content types, no per-type dialect. The database trigger
`cms_validate_blocks` repeats the structural envelope for writers that
bypass the domain.

The legacy platform-wide `apps.api.Page` model and `/api/pages/` endpoints
are untouched: they are the existing unscoped CMS surface and their migration
into this site-scoped domain is a later story. Nothing here claims that
legacy content has been re-homed.

## Page: models, slugs, hierarchy and metadata (P2-CMS-002)

`Page` is the first concrete content type: a multi-table child of
`SiteContent` that inherits identity, Site ownership, status, locale,
authorship and metadata, and adds routing. A translation is a sibling row in
another locale — the trees are per language (still no translation workflow).

| Field | Contract |
| --- | --- |
| title | Required, max 255 characters, in this row's language |
| slug | One route segment. Normalized before validation (lowercased, every run of other characters collapsed to a single hyphen, trimmed) and constrained to `[a-z0-9]+(-[a-z0-9]+)*` |
| parent | Self-FK with `PROTECT`. Must share the page's Site and locale, never be the page itself or one of its ancestors, and the hierarchy is capped at 15 levels |
| path | Computed full route within Site and locale (`/about/people`), `editable=False`, rebuilt from the slug chain on every save |
| layout | Optional approved layout code (`[A-Z][A-Z0-9_-]{0,63}`), resolved by the rendering layer. A reference — not a template file, not a secret |
| seo | Allowlisted object: `meta_title` (≤120), `meta_description` (≤300), `og_image_ref` (≤512). Unknown keys and non-string values are rejected in the domain; `jsonb_typeof = 'object'` at the database |
| visibility | `PUBLIC` served and listed, `UNLISTED` served only by its direct route, `HIDDEN` never served publicly |
| position | Sibling ordering hint; ties are broken by `id` so listings are stable |
| is_homepage | Designates the page that serves the Site root. At most one per Site |

### Hierarchy rules

- **Same Site, same language.** A parent must carry the child's `site_id`
  and `locale`; cross-Site and cross-locale parenting are rejected, so a
  subtree can never straddle tenants or languages.
- **No cycles.** The domain walks the ancestor chain on every save and
  rejects a page that becomes its own ancestor; the database trigger repeats
  the walk with a bounded recursive CTE (`page_acyclic`, `page_depth`) so
  raw SQL cannot introduce one either. Self-parenting is refused by the same
  domain and trigger (`page_parent_not_self`) — Django's declarative
  constraints cannot reference the parent-table `id` from an MTI child, so
  the trigger is the database-level enforcement point.
- **`PROTECT` both ways.** Deleting a parent with children fails, and a Site
  that owns pages cannot be deleted.
- **The language is fixed at creation.** Changing `locale` afterwards is
  rejected ("create a translated page instead"), which keeps parent/locale
  agreement and route uniqueness meaningful.

### Route and canonical policy

`path` *is* the canonical route: it is stored, not derived at request time,
and it is unique per `(site, locale, path)` — no duplicate full routes
within a Site and locale. Sibling slug uniqueness follows from this, because
siblings share their parent's prefix; two pages may reuse a slug when they
sit under different parents (`/a/slug` vs `/b/slug`). Two Sites, or two
locales of one Site, freely reuse the same path.

Physically, `site` and `locale` live on the shared `cms_sitecontent` row
while `path` lives on `cms_page`, so this key cannot be a plain index on one
table. It is enforced twice: in the domain (`Page._assert_route_is_free`
raises a friendly `ValidationError`) and in the database by the
`cms_validate_page` trigger, which joins the parent row and serializes
writers per Site with an advisory lock so racing saves cannot both commit
(`page_route_uniq`). The Page table's own index (`page_parent_idx` on
`(parent)`) serves subtree reads; tenant scoping for everything else comes
from the SiteContent ownership indexes and the route key itself.

### Homepage

`is_homepage` marks the page that serves the Site root; zero homepages is
valid ("where configured"), two never are. Replacement goes through
`services.pages.set_as_homepage`, which clears the previous flag and sets
the new one inside one transaction — a failed swap leaves the old homepage
in place. The database trigger (`page_homepage_uniq`) enforces the same
rule against concurrent writers, so even two racing transactions resolve to
exactly one homepage. The flag is site-wide, not per locale, and it does
not publish anything: the serving layer still applies the published rules.

### Visibility and serving

The public URL space is served exclusively through
`apps.cms.selectors.pages`: `published_page` returns a route's page only
when `status = PUBLISHED` and visibility is `PUBLIC` or `UNLISTED`;
`public_pages` lists `PUBLIC` published pages in sibling order;
`homepage_of` reads the root candidate. **Draft pages are never publicly
served**, and `HIDDEN` pages are never served publicly — a draft homepage
is configurable but not renderable. No endpoint mounts these selectors yet;
the PAGES capability stays `PLANNED` until public serving ships, so no
module gate has opened.

### URL history and redirect policy

When `services.pages.change_route` renames or re-parents a page it records
every vanished path — for the page *and its whole subtree*, since moving an
ancestor moves every descendant route — as `PageRedirect` rows keyed by
`(site, locale, old_path)`. The policy:

- **Live routes win.** A redirect is consulted only when no live page
  matches the request; a page recreated on an old path removes its own
  redirect row.
- **Redirects are re-pointed, not chained.** A redirect always targets the
  page's current path, so history never grows a chain of hops.
- **History belongs to the page.** Deleting a page deletes its redirects
  (`CASCADE`); the Site itself is `PROTECT`-ed either way.
- **A route change is transactional.** Path recomputation, subtree
  re-saves and redirect rows commit together or not at all.

### API contract

`apps.cms.api.serializers.PageSerializer` extends the shared contract:
`id`, `site`, `path`, `is_homepage`, `status`, authorship and timestamps
are server-managed; `title`, `slug`, `layout`, `seo`, `visibility`,
`position`, `metadata` and `blocks` are writable in editable workflow states;
`submitted_by`, `reviewed_by` and `review_comment` are server-managed.
`parent` is accepted on create and update only within the owning Site and
locale — moves go through `change_route` so URL history is recorded, and the
language is fixed at creation. The
[shared review/publishing workflow](./cms-workflow.md) owns all status
transitions. The Site-scoped Page endpoints are mounted under
`/api/v1/sites/{site_pk}/pages/`; their request and response schemas are
generated from `PageSerializer`.
